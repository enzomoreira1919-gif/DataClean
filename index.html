01 / O PROBLEMA

Quando uma tabela começa a atrapalhar?

Imagine uma loja que registra o pedido, o cliente e todos os produtos em uma única linha. Parece simples no início, mas os mesmos dados acabam repetidos e difíceis de atualizar.

↻

Anomalia de atualização

Se o endereço do cliente aparece em dez linhas, é preciso corrigir todas. Uma linha esquecida deixa o banco inconsistente.

＋

Anomalia de inserção

Talvez não seja possível cadastrar um produto antes de existir um pedido, porque as informações estão misturadas.

×

Anomalia de exclusão

Ao excluir o único pedido de um produto, informações sobre o próprio produto podem desaparecer junto.

Importante: os nomes, clientes, pedidos e produtos deste projeto são fictícios e servem apenas para fins didáticos.

02 / OS CONCEITOS

Três etapas para organizar os dados

Vamos usar um mesmo exemplo e evoluir a estrutura passo a passo. As formas normais são regras de organização baseadas nas relações entre os atributos.

1FN
PRIMEIRA FORMA NORMAL

Um valor por campo

Cada coluna deve guardar um valor atômico para cada linha, sem listas de produtos ou grupos repetidos dentro de uma célula.

✕ Antesprodutos = "Mouse, Teclado"
✓ Depoisuma linha para cada item
Atomicidade
2FN
SEGUNDA FORMA NORMAL

Depender da chave inteira

A tabela precisa estar na 1FN e cada atributo não-chave deve depender da chave candidata inteira, não apenas de uma parte de uma chave composta.

✕ Antes(pedido_id, produto_id) → nome_produto
✓ Depoisproduto_id → nome_produto
Sem dependência parcial
3FN
TERCEIRA FORMA NORMAL

Evitar dependências transitivas

A tabela precisa estar na 2FN. Atributos não-chave devem depender da chave, da chave inteira e de nada além da chave — sem depender de outro atributo não-chave.

✕ Antespedido_id → cliente_id → nome_cliente
✓ Depoisnome_cliente fica em clientes
Sem dependência transitiva
ƒ
Aprofundamento: dependência funcional

Escrevemos X → Y quando o valor de X determina unicamente o valor de Y dentro da relação. Uma chave primária identifica cada linha; uma chave estrangeira referencia uma chave de outra tabela.

04 / LABORATÓRIO SQL

Veja a estrutura em código

O exemplo foi escrito para PostgreSQL. Copie o script para um banco de testes vazio ou abra o arquivo completo no repositório.

sql/normalizacao.sql · PostgreSQL
-- Cada entidade tem sua própria tabela.
CREATE TABLE clientes (
    cliente_id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome       VARCHAR(100) NOT NULL,
    cidade     VARCHAR(80) NOT NULL
);

CREATE TABLE pedidos (
    pedido_id  INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    cliente_id INTEGER NOT NULL REFERENCES clientes(cliente_id),
    data_pedido DATE NOT NULL
);

CREATE TABLE produtos (
    produto_id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome       VARCHAR(100) NOT NULL,
    preco      NUMERIC(10,2) NOT NULL CHECK (preco >= 0)
);

CREATE TABLE itens_pedido (
    pedido_id  INTEGER NOT NULL REFERENCES pedidos(pedido_id),
    produto_id INTEGER NOT NULL REFERENCES produtos(produto_id),
    quantidade INTEGER NOT NULL CHECK (quantidade > 0),
    preco_unitario NUMERIC(10,2) NOT NULL CHECK (preco_unitario >= 0),
    PRIMARY KEY (pedido_id, produto_id)
);
ⓘ O preço unitário do item é registrado no momento da compra para preservar o histórico mesmo que o preço atual do produto mude.
QUERY 01

Consultar pedidos com o nome do cliente

O JOIN relaciona as tabelas usando as chaves correspondentes.

SELECT p.pedido_id, c.nome, p.data_pedido
FROM pedidos AS p
JOIN clientes AS c
  ON c.cliente_id = p.cliente_id
ORDER BY p.pedido_id;

05 / BOAS DECISÕES

Normalizar não é apenas dividir tabelas

01

Identifique as chaves

Entenda o que identifica cada linha e quais atributos dependem dela.

02

Preserve os relacionamentos

Use chaves estrangeiras e restrições para proteger a integridade referencial.

03

Teste o resultado

Compare consultas antes e depois. Uma decomposição bem feita deve preservar os dados e evitar combinações incorretas.

Limitação a considerar

A normalização reduz redundâncias e anomalias, mas não resolve sozinha todos os problemas de desempenho, segurança ou qualidade dos dados. A modelagem depende das regras reais do negócio e deve ser validada com exemplos e consultas.
